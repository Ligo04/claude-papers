# 练习题

## 基础（5 题）

### Q1: 本文解决什么问题？为什么现有方法不够好？

<details>
<summary>答案</summary>

本文解决的是**自动为 3D 模型生成碰撞体**的问题。

现有方法（V-HACD、CoACD）使用凸包分解，存在三个问题：
1. **性能差**：凸包的顶点/面数不可控，碰撞检测开销大
2. **不可编辑**：输出形状无法在 DCC 工具中方便修改
3. **输入限制**：通常需要流形/水密网格

本文用参数化基元（盒子、球、胶囊等）代替凸包，这些基元被物理引擎原生支持，碰撞检测更快，且可以在 Blender/UE 中直接编辑。

</details>

### Q2: 线性算子 Q = nn^T 的物理含义是什么？

<details>
<summary>答案</summary>

Q = nn^T 是法线 n 与自身的**外积**，生成一个 3×3 矩阵。

物理含义：
- 它是一个**投影矩阵**，将任意向量投影到法线方向
- 对单个面：特征值为 (area, 0, 0)，最大特征向量就是法线
- 对多个面合并 Q_total = Σ Qᵢ：最大特征向量代表这组面的"主法线方向"

关键性质：**可加性** — Q_a + Q_b 直接代表两组面的合并方向信息，不需要重新计算。

</details>

### Q3: 该方法支持哪些基元类型？

<details>
<summary>答案</summary>

支持 6 种基元：
1. **定向包围盒（OBB）**：最基础，10 个浮点参数
2. **球体**：最便宜的碰撞检测，4 个参数
3. **胶囊体**：两端为半球的圆柱，7 个参数
4. **有盖圆柱体**：7 个参数
5. **棱台（Frustum）**：锥形结构，8 个参数
6. **等腰梯形棱柱**：处理屋顶等结构，11 个参数

所有基元都是凸的，且有解析体积公式。

</details>

### Q4: 代价函数 C(p₀, p₁) = V(merge) - V(p₀) - V(p₁) 为什么有效？

<details>
<summary>答案</summary>

这个代价函数衡量的是**合并引入的额外体积**（超量体积）。

有效性原因：
- **正值**：合并增大了体积，说明两基元不太适合合并
- **零值**：合并不增加体积（如完全重叠的基元），免费合并
- **负值**：合并反而减少了体积（消除了重叠），是有益合并

优势：
- 不需要计算网格体积（不要求水密输入）
- 只需基元自身的解析体积公式
- 计算极快

贪心策略始终选择引入最少额外体积的合并，保证碰撞体尽量紧贴输入。

</details>

### Q5: 特征分解如何确定基元的方向？

<details>
<summary>答案</summary>

对合并后的 Q 做特征分解 Q = WΛW⁻¹：

- **w₂**（最大特征值对应）：面积加权的主法线方向 → OBB 的最短轴（厚度方向）
- **w₁**（中间特征值）：次要法线方向 → OBB 的中间轴
- **w₀**（最小特征值）：面积最少的方向 → 圆柱/胶囊的轴向

这三个正交向量构成基元的**局部坐标系**，所有后续参数拟合都在这个坐标系下进行。

直觉：如果一组面形成一个管状结构，法线在侧面"散开"（大特征值），而管轴方向法线很少（小特征值），所以最小特征值的特征向量自然对齐管轴。

</details>

## 中级（5 题）

### Q6: 为什么要添加切线正则化项 ε·tt^T？

<details>
<summary>答案</summary>

当多个面**共面**时，它们的法线相同，Q = Σ aᵢ·nn^T 只是 nn^T 的标量倍数。此时特征分解退化：只有一个非零特征值，另外两个特征向量不确定（任何垂直于 n 的向量都行）。

添加 ε·tt^T 的作用：
- 在切平面内引入一个偏好方向
- 打破共面退化，使特征向量确定
- ε 很小，不会显著影响非退化情况

对三角形：切线由最长边推导（模拟四边形的对角线方向）
对四边形：切线为两条对角线的中间向量

这是 QEM 中退化问题的已知修复手段的变体。

</details>

### Q7: 基元类型权重 k(type) 如何影响输出？有什么设计考量？

<details>
<summary>答案</summary>

权重通过 V'(p) = k(type) · V(p) 修改体积计算，影响基元类型选择：
- k = 1.0（盒子/球/胶囊）：不惩罚，物理引擎有原生优化
- k = 1.05（圆柱）：略微惩罚，因为细长圆柱和胶囊视觉差异小但胶囊更快
- k = 1.4（梯形棱柱）：较大惩罚，需要用凸包表示
- k = 2.1（棱台）：最大惩罚，需要量化后使用

设计考量：
1. **下游性能**：物理引擎对基元的支持程度不同
2. **精度-速度权衡**：复杂基元更贴合但碰撞检测更慢
3. **可编辑性**：标准基元在 DCC 工具中更易修改
4. **可调性**：不同游戏类型可用不同权重（精确平台 vs 粗略解谜）

</details>

### Q8: 面级归并（face-based）相比顶点级归并（vertex-based）有什么优势？

<details>
<summary>答案</summary>

传统 QEM 合并**顶点**，每个顶点被一个基元覆盖。如果直接套用这种方式：
- 输出为每个顶点周围的小基元
- 基元之间有空隙（不覆盖面的中间区域）
- 严重偏离输入表面

面级归并的优势：
1. **完整覆盖**：每个面的所有顶点都被其归属基元包含
2. **允许重叠**：一个顶点可被多个基元覆盖（共享顶点的面属于不同基元）
3. **基元并集覆盖整个表面**：不留空隙
4. **邻接关系自然**：面邻接定义了合并图的边

论文中 Fig. 11 展示了顶点级 vs 面级的对比，面级方法明显更好。

</details>

### Q9: 断开组件（disconnected components）如何处理？为什么需要特殊处理？

<details>
<summary>答案</summary>

问题：输入网格可能有多个断开的组件（如不同部件组合的模型）。基于面邻接的合并只能在连通组件内部进行，可能无法达到目标基元数 N。

处理方式（分两阶段）：
1. **阶段一**：正常基于面邻接合并，直到所有边耗尽
2. **阶段二**：如果 |P| > N，添加所有组件对之间的虚拟边，形成全连接图继续合并

复杂度：O(|C|²) 对组件对，但实际中组件数通常很少。

另外的缓解措施：
- **顶点去重**：距离很近的顶点合并，连接原本断开的组件
- **体积阈值**：跨组件合并通常代价很高，会被阈值过滤

设计哲学：断开组件通常代表不同的凸物体，**不应该**合并。所以先基于拓扑合并（尊重几何结构），只在必须时才强制合并。

</details>

### Q10: 论文如何验证"仿真相似性"？这个评估方法有什么局限？

<details>
<summary>答案</summary>

验证方法：
1. **定性**：在碰撞体上投掷 5000 个球，目视检查行为是否与原始网格相似
2. **定量几何**：单向 Hausdorff/Chamfer 距离（碰撞体表面 → 输入表面）
3. **性能**：测量仿真帧时间（wall-clock time）

局限：
- **没有仿真相似性的标准度量**：目前不存在好的方式量化两个碰撞行为有多"相似"
- **单向距离不完整**：不惩罚碰撞体没覆盖到的区域（但论文解释这是刻意的，因为封闭保证已经满足）
- **硬件依赖**：性能结果依赖具体 CPU 和物理引擎实现
- **测试场景单一**：只测了球的自由落体，未测试角色控制器等复杂场景
- **基元数手动选择**：每个模型的目标数是手动决定的，不同数量下结果可能不同

</details>

## 高级（5 题）

### Q11: 为什么忽略交叉体积（Eq.4 vs Eq.5）是合理的？在什么情况下会失败？

<details>
<summary>答案</summary>

Eq.4（无交叉项）：C = V(merge) - V(p₀) - V(p₁)
Eq.5（含交叉项）：C = V(merge) - V(p₀) - V(p₁) + V(p₀ ∩ p₁)

忽略的理由：
1. **计算成本**：精确交叉体积需要布尔运算（mesh booleans），即使近似（rejection sampling）也要 30× 时间
2. **实际影响小**：对游戏资产（干净拓扑），相邻基元重叠有限
3. **实验验证**：Fig. 16 的消融实验显示改进微乎其微

会失败的场景：
- **高度重叠的区域**：如球体套球体、大量基元堆叠的复杂结构
- **非流形输入**：kit-bashing（模型拼接）产生的大面积重叠
- **初始化退化**：面积非常小的面可能产生高度重叠的初始基元
- **合并后期**：当剩余基元很少时，大基元之间的重叠可能显著

根本原因：贪心算法的局部最优性在有全局耦合（交叉体积）时会退化。

</details>

### Q12: 如何将此方法扩展到动态/可变形物体的碰撞体生成？

<details>
<summary>答案</summary>

当前方法只处理静态刚体。扩展到动态物体需要解决：

**方案 1：骨骼绑定分解**
- 对每个骨骼影响的面子集独立分解
- 运行时每帧用骨骼变换更新基元位置/方向
- 问题：关节处基元可能分离或穿透

**方案 2：运动状态感知分解**
- 预计算关键帧的"最优"分解
- 运行时插值基元参数
- 问题：不同姿态可能需要不同拓扑的分解

**方案 3：自适应分解**
- 维护面→基元的映射
- 变形时增量更新 Q 矩阵和基元参数
- 大变形触发局部重新分解
- 问题：增量更新可能累积误差

**核心挑战**：
- 线性算子 Q 基于初始几何计算，变形后不再有效
- 面邻接可能变化（如布料撕裂）
- 需要平衡"重计算频率"和"碰撞精度"

SQEM (Tkach et al. 2013) 在这个方向有一些工作，但限于球体。

</details>

### Q13: 贪心策略的最坏情况是什么？如何改进？

<details>
<summary>答案</summary>

**最坏情况**：
早期一个"看起来便宜"的合并阻止了后续更好的全局解。

例子：两个L形面集，各自合并为紧凑的OBB很好。但如果算法先把L的拐角处与另一个L合并，导致两个L都变成巨大的包围盒。

**具体表现**：
- 薄壁结构中，横向合并（跨壁面）比纵向合并代价更低但效果更差
- 对称结构中，打破对称的合并可能局部最优但全局次优

**可能的改进**：

1. **延迟提交（lazy evaluation）**：
   - 合并前重新计算代价（当前已有的惰性删除只检查过期）
   - 代价变化超过阈值则重新入队

2. **k-way 合并**：
   - 不是每次合并 2 个，而是考虑合并 k 个邻居的所有组合
   - 复杂度 O(C(k,2))，但 k=3 或 4 即可显著改善

3. **多分辨率策略**：
   - 先用粗粒度分解到中间数量
   - 再用精细代价函数进一步简化
   - 类似 coarse-to-fine 策略

4. **模拟退火/禁忌搜索**：
   - 允许偶尔接受代价增加的合并
   - 用禁忌表避免循环

5. **全局代价项**：
   - 加入正则化：惩罚不均匀的基元大小分布
   - 类似 Lloyd 迭代的全局均衡

</details>

### Q14: 论文声称 O(|F| log |F|) 复杂度。分析实际瓶颈在哪，如何并行化？

<details>
<summary>答案</summary>

**复杂度来源**：
- 初始化 Q：O(|F|)
- 初始化优先队列：O(|E| log |E|)，|E| ≈ 3|F|（三角网格）
- 主循环：每次合并 O(d·log|E|)，d 是平均度数，总共 O(|F|·d·log|E|)
- 特征分解：每次合并重新计算，O(27)（3×3 固定大小）
- 基元拟合：O(|points_in_primitive|)

**实际瓶颈**：
1. **基元拟合中的点遍历**：合并后需遍历所有子集面的顶点来拟合参数。随着合并进行，基元包含的点数增长，后期每次合并的拟合成本线性增长。
2. **优先队列更新**：合并后需更新所有邻居的代价，涉及再次拟合。
3. **缓存不友好**：循环链表遍历有大量指针追踪。

**并行化策略**：

1. **独立合并并行化**：
   - 图着色：给面图着色，同色面互不相邻
   - 同色面可同时合并（不会冲突）
   - 类似并行 QEM 的方法

2. **基元拟合并行化**：
   - 每种基元类型的拟合相互独立
   - 点集扫描可 SIMD 向量化（特别是投影操作）

3. **分区策略**：
   - 用空间哈希或 BVH 将网格分区
   - 每个分区独立分解到某个中间数量
   - 最后跨分区合并

4. **GPU 加速**：
   - 特征分解和点投影适合 GPU
   - 优先队列是瓶颈（不好并行），可用近似策略

</details>

### Q15: 如果要将这个方法集成到游戏引擎的自动化 pipeline 中，需要解决哪些工程问题？

<details>
<summary>答案</summary>

**1. 自动参数选择**
- 目标基元数 N：可基于模型复杂度启发式设定（如 |F|/100）
- 体积阈值：可基于 AABB 体积的百分比
- 权重：可暴露为"精度 vs 性能"滑条
- 挑战：不同类别模型（角色/建筑/植物）需要不同策略

**2. 增量更新**
- 美术修改模型后不必全部重算
- 只对修改区域重新分解
- 需要维护面→基元映射的持久化

**3. LOD 集成**
- 不同 LOD 级别用不同 N 值
- 远处用粗糙碰撞体，近处用精细碰撞体
- 需要 LOD 切换时碰撞行为的连续性

**4. 验证与反馈**
- 自动检测"坏"碰撞体（如完全封闭通道、悬浮基元）
- 可视化基元与输入的偏差热力图
- 允许美术手动修正特定基元

**5. 格式与引擎支持**
- 梯形棱柱和棱台需要凸包化
- 不同引擎（Unity/UE/Godot）支持的基元不同
- 需要适配层处理序列化格式

**6. 性能预算集成**
- 与引擎的 profiler 集成
- 基于碰撞热点自动建议更精细的分解
- 预算分配：关键物体用更多基元，背景物体用更少

**7. 批处理**
- 大型项目可能有上千个模型需要处理
- 需要后台批处理 + 变更检测
- 缓存中间结果（Q 矩阵、邻接图）

**8. 边缘情况处理**
- 极小面（面积趋近零）的数值稳定性
- 完全平坦模型（如地面/墙壁）
- 数百万面的扫描模型的内存管理

</details>
