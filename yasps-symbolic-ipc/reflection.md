# 反思 —— 扩展、脆弱假设、失败模式

## 如果由我来扩展这篇论文

1. **把非线性参数化作为一等公民,并配结构感知投影。** 降维投影(第 5.4 节)只在参数化线性时触发。能否检测
   *部分* 线性或低秩曲率项,从而仍能投影一个缩减的内层 Hessian?神经场或样条蒙皮参数化是显然的目标——一个
   "曲率秩分析"pass 扫过符号图,可把那个 44× 杠杆推广到仿射/笼形之外。

2. **内置的、参数化通用的 CCD。** YASPS 把碰撞检测推给外部,因为轨迹依赖参数化。但关系式 IR *知道* 每个图元
   的参数化的符号形式——能否从同一份描述 **生成** CCD(从 JOIN/UNION 图导出保守界),而非手工提供?这会补上
   最大的"它不是完整仿真器"的缺口。

3. **可微仿真 / 逆向设计。** 整个后端是一个符号微分引擎;暴露 *仿真结果* 对材料/形状参数的端到端梯度(而不只
   是一个牛顿步),会把 YASPS 变成逆向设计/系统辨识工具。IR 已支持这套机制;缺的是穿过求解器和(外部)步进
   的微分。

4. **自动调优能量重表述。** 第 10.4 节表明手动把 `Ψ(F(x))` 通过额外 JOIN 具体化能带来 1.56×–2×。这是一个
   编译器可以自动搜索的 *图重写*:枚举切点,估计投影尺寸 vs 额外 Jacobian 乘法的成本,挑最优。一个由成本模型
   驱动、在边界节点拆分上做优化的优化器。

5. **超越 IPC 负载。** JOIN/UNION + 符号微分 + 块稀疏装配这套栈本质上不限于接触。仅布料、仅 FEM、MPM 耦合,
   甚至非物理的关系式最小二乘(光束法平差、图优化)都能搭这套 IR。这个抽象在"局部项高度并行"假设失效前能伸到
   多远?

6. **多 GPU / 核外扩展。** 基准最多到约 60k 顶点 / 25 只 bunny。把块稀疏 Hessian 和 PCG 分布到多 GPU,以及依赖
   动态碰撞连接关系的索引生成,都很棘手但高价值。

## 哪些开放问题仍存

- **步进/收敛超出范围,但起决定作用。** 基准里 Stark 在碰撞上无法收敛(64/200 帧)。YASPS 把 `x` 交给你就
  撒手不管线搜索/阻尼——但一个以鲁棒性为卖点的框架,最终得对全局收敛表态,或至少给用户工具去诊断它。
- **JIT/编译延迟 vs 交互性。** 首次 `minimizeEnergy` 触发 nvcc 编译;新的压缩尺寸在仿真中途触发更多 JIT。
  摊销成本对离线仿真没问题,但交互/实时用途(IPC 越来越多地被应用于此)要的是有界的每步延迟。kernel 缓存
  的预热有多可预测?
- **只比了速度和 LOC,没比精度/鲁棒性。** 评测显示 YASPS *一样快* 且 *更可扩展*,但对数值精度、能量守恒、
  或在刚硬/极端接触下的鲁棒性相对 GIPC 说得很少。"性能相当" ≠ "解相同"。
- **生成代码质量的天花板。** YASPS 的微分+装配阶段一直慢于 GIPC 的手工调优 kernel。这个差距有多少是通用性
  本质决定的,有多少可以靠更好的后端(寄存器分配、融合、占用率调优)补上?

## 哪些假设脆弱

| 假设 | 为何是承重的 | 何时崩裂 |
|---|---|---|
| 参数化是 **线性** 的 | 启用降维投影(44× 杠杆)和例子里的 CCD | 任何非线性参数化(蒙皮、神经场)——性能故事坍缩到只剩块压缩 |
| 局部项 **高度并行且小** | 支撑每实例 GPU kernel 和"局部块保持小" | 大支撑/稠密耦合的能量(如全局约束、长程力) |
| **不同压缩 Hessian 尺寸的数量很小** | 让"每尺寸一 JIT"的 kernel 数可控 | 高度异构、有许多不同有效尺寸的场景 ⇒ 大量 JIT 编译 |
| **外部 CCD** 每步提供正确的动态连接关系 | YASPS 的索引生成/装配假定碰撞对有效 | 不匹配或非线性不兼容的 CCD 会悄悄破坏接触 |
| **UNION 最坏尺寸是可收回的** | 块压缩 + 降维投影撤销填充浪费 | 若大多数块 *保持* 接近最大尺寸(如全 ABD 场景),节省缩水、填充成纯开销 |
| **GPU 内存装得下压缩全局 Hessian** | 单 GPU 设计 | 超大场景超出设备内存;没展示核外路径 |

## 实际中可能崩在哪

- **全 ABD 或全非线性场景:** UNION 最大尺寸开销付了却收回很少,且降维投影可能不适用——YASPS 可能丢掉它对
  专门系统的总时间优势。
- **实时/交互场景:** JIT 编译延迟和缺少内置步进让它作为即插即用实时引擎很别扭;它定位为离线/研究框架。
- **刚硬或病态接触:** 没有规定的线搜索/收敛策略,发散(如 Stark 表现的)是 *用户* 的问题——在非专家手里脆弱。
- **调试生成的 CUDA:** 当用户的 130 行能量产出错误结果,失败浮现在 JIT 生成、CSE 搅过、分别链接的 kernel 里
  ——远比手写代码难调。恰恰在你最需要看穿它时,抽象漏了。
- **移植离开 CUDA/NVIDIA:** 后端是 CUDA 专属的(且依赖 Eigen 的模板化 GPU EVD、NVIDIA Warp);其他加速器需要
  新的代码生成后端。

## 元层面的收获

这篇论文经久的教训比 IPC 更宽广:**你为了让系统 *正确且通用* 而必须暴露的结构信息(关系、参数化备选项),
正是你为了让它 *快* 而需要的信息(稀疏、投影尺寸缩减)。让这份结构显式且可微,你就避开了经典的通用性-vs-性能
权衡**——代价是构建(并信任)一个编译器。上面那些脆弱性,大多是为这个编译器、以及为让它最佳优化得以触发的
线性假设所付的账单。
